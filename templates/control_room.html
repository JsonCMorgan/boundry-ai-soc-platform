🛡 MITRE ATT&CK Reference — Techniques Monitored by This System ▼
T1110 Brute Force
Credential Access
What you see in the feed
Many LOGIN_FAILED events from the same IP against the same username. Threshold: 5+ failures. May end with a LOGIN_SUCCESS (attack succeeded).
↔ vs T1110.003 Spray: brute force = one account, many passwords.
↔ vs T1110.004 Stuffing: brute force tries guesses, stuffing uses a known leaked list.
Full Playbook: Detection, Mitigation & IR →
T1110.003 Password Spraying
Credential Access
What you see in the feed
LOGIN_FAILED events from one IP against many accounts, each with a low failure count (1–2 per account). Extra field contains sprayed_password=X.
↔ vs T1110 Brute Force: spray = many accounts, one password — designed to stay below lockout thresholds.
↔ vs T1110.004 Stuffing: spray uses a common password; stuffing uses unique credentials per account.
Full Playbook: Detection, Mitigation & IR →
T1110.004 Credential Stuffing
Credential Access
What you see in the feed
LOGIN_FAILED from same IP, 4+ different accounts — no sprayed_password marker. Suggests a leaked credential list. A subsequent LOGIN_SUCCESS from the same IP = CRITICAL.
↔ vs T1110.003 Spray: stuffing uses unique logins per account from a breach dump, not one shared password.
↔ vs T1110 Brute Force: stuffing hits many accounts once each; brute force hits one account many times.
Full Playbook: Detection, Mitigation & IR →
T1190 Exploit Public-Facing Application
Initial Access
What you see in the feed
SEARCH events with SQL syntax in the query field: ' OR, --, UNION SELECT, DROP TABLE, 1=1. Attacker is injecting SQL into the search box.
↔ vs T1059.007 XSS: SQLi targets the database; XSS targets the browser of another user.
Key indicator: SQL keywords (SELECT, UNION) vs HTML/JS tags (<script>).
Full Playbook: Detection, Mitigation & IR →
T1059.007 JavaScript (XSS)
Execution
What you see in the feed
XSS_ATTEMPT events with HTML or JavaScript in the payload: <script>, onerror=, javascript:, <svg onload=. Goal: execute code in another user's browser.
↔ vs T1190 SQLi: XSS targets users' browsers to steal cookies or redirect; SQLi targets the database.
Key indicator: HTML/JS syntax vs SQL keywords.
Full Playbook: Detection, Mitigation & IR →
T1083 File & Directory Discovery
Discovery
What you see in the feed
DIRECTORY_TRAVERSAL events with ../ path sequences: ../../etc/passwd, %2e%2e%2f (URL-encoded). Attacker is trying to read files outside the web root.
↔ vs T1548 Priv Esc: traversal probes the filesystem via paths; priv esc probes restricted routes inside the application.
Both are discovery-type behaviours but at different layers.
Full Playbook: Detection, Mitigation & IR →
T1548 Abuse Elevation Control Mechanism
Privilege Escalation
What you see in the feed
PRIV_ESC_ATTEMPT events after a LOGIN_SUCCESS: authenticated user hitting /admin, /control-room, /.env, /api/admin. They're logged in but probing for higher access.
↔ vs T1083 Traversal: priv esc is about application routes (HTTP 403 doors); traversal is about filesystem paths.
Key pattern: always follows a successful login from the same IP.
Full Playbook: Detection, Mitigation & IR →
T1589.001 Gather Victim Identity Info
Reconnaissance
What you see in the feed
ACCOUNT_ENUM events: same IP probing 6+ different usernames rapidly. Attacker is mapping which accounts exist before launching a targeted attack.
↔ vs T1110 Brute Force: enumeration just checks existence (no password attempts); brute force comes after — it uses the confirmed usernames.
Think of this as the "shopping list" phase before the attack.
Full Playbook: Detection, Mitigation & IR →
T1078 Valid Accounts
Defense Evasion
What you see in the feed
LOGIN_SUCCESS with new_ip=true or unusual_hour=true in the extra field. Real credentials, no failure storm — but something about the context is off. Could be account takeover via phishing or credential theft.
↔ vs T1110 Brute Force: T1078 succeeds immediately with no prior failures — credentials were already stolen, not guessed.
Hardest to detect because it looks like a legitimate login.

⚡ Rapid TTP Disambiguation — Differential Signal Analysis Similar detection signals, different techniques — here's how to tell them apart at first glance
Attack Family 1 Credential-Based Attacks — all produce LOGIN events
You see: LOGIN_FAILED and/or LOGIN_SUCCESS events. First question: What is the IP-to-account ratio?
Technique IP Pattern Account Pattern Smoking Gun Signal Worst Case
T1110
Brute Force		 1 IP → 1 account High failures on same username (5+) Many LOGIN_FAILED → same user, same IP. Attempt count rising over time. LOGIN_SUCCESS from that same IP after failure storm = account compromised
T1110.003
Password Spray		 1 IP → many accounts Low failures per account (1–2 each) extra field on LOGIN_FAILED shows sprayed_password=X — same password tried across all accounts One LOGIN_SUCCESS after low-failure spray = the sprayed password worked on at least one account
T1110.004
Credential Stuffing		 1 IP → many accounts Low failures per account — no shared password marker Same as spray pattern but NO sprayed_password field. Each account gets a unique credential → suggests a breach dump. LOGIN_SUCCESS mid-spray = one real breached credential matched a live account
T1589.001
Account Enum		 1 IP → rapid probing Rapid username probes, very low failure depth ACCOUNT_ENUM events with 6+ different usernames from same IP, very fast cadence. Pre-attack reconnaissance — the shopping list phase. Often precedes brute force or stuffing on the confirmed usernames — watch for followup LOGIN_FAILED burst
T1078
Valid Accounts		 Any IP Zero failures — credentials already known LOGIN_SUCCESS with new_ip=true or unusual_hour=true. No failure precursor. Credentials were stolen (phishing/breach), not guessed. Hardest to detect — looks like a legitimate login. Follow-up PRIV_ESC_ATTEMPT from same session confirms ATO (Account Takeover)
QUICK CALL: Many fails, 1 account → Brute  |  Few fails, many accounts + spray marker → Spray  |  Few fails, many accounts, no marker → Stuffing  |  Rapid probes, no cred attempts → Enum (Recon)  |  Success, no failures, weird context → ATO (T1078)
Attack Family 2 Web Injection Attacks — all produce suspicious HTTP payload events
You see: SEARCH / XSS_ATTEMPT / DIRECTORY_TRAVERSAL events with a suspicious payload. First question: What language is in the payload?
Technique Payload Language Example IOC Target (What They Want) Blast Radius if Successful
T1190
SQL Injection		 SQL syntax
SELECT, UNION,
OR 1=1, DROP, --		 ' OR '1'='1
UNION SELECT username,password		 The database — credential extraction, data dump, auth bypass, or destructive payload (DROP TABLE) Full DB compromise. All credentials, PII, financial data exposed. Complete data confidentiality breach.
T1059.007
XSS		 HTML / JavaScript
<script>, onerror=,
javascript:, <svg>		 <script>alert(1)</script>
<img onerror=fetch(...)>		 Other users' browsers — session cookie theft, credential harvesting, malicious redirects, defacement Stored XSS = every user who loads the page is compromised. Session hijacking at scale.
T1083
Dir Traversal		 File path syntax
../, %2e%2e%2f,
/etc/passwd, \windows\		 ../../etc/passwd
%2e%2e%2fsystem32		 The server filesystem — reading config files, credentials, private keys, source code outside the web root Server credentials and private keys exposed. Could enable full server takeover if /etc/shadow or .env files are reached.
QUICK CALL: SQL keywords in payload → SQLi (targets DB)  |  HTML/JS tags in payload → XSS (targets other users)  |  Path sequences (../) → Traversal (targets filesystem)
Attack Family 3 Post-Authentication Privilege Abuse — both require a prior LOGIN_SUCCESS
You see: LOGIN_SUCCESS followed by suspicious activity. First question: Was the login itself suspicious, or is it what they did AFTER?
Technique The Login Event Post-Login Activity Smoking Gun CISSP Principle Violated
T1548
Priv Esc		 Normal login — nothing anomalous about the login itself. Standard IP, standard hour. Suspicious routes accessed after login: /admin, /.env, /api/admin PRIV_ESC_ATTEMPT events. The indicator is the route pattern, not the login context. Least Privilege (IAM). Authenticated user probing beyond their authorised scope.
T1078
Valid Accounts		 The login IS the anomaly — new_ip=true or unusual_hour=true in the extra field May appear normal — no PRIV_ESC events. The threat actor behaves legitimately to avoid detection. Contextual anomaly on the LOGIN_SUCCESS itself. No failure precursor. Zero brute force indicator. Authentication integrity (D5 IAM). Credential compromise via out-of-band vector (phishing, breach).
QUICK CALL: Weird login context (new IP / odd hour) → T1078 ATO — investigate the login event itself  |  Normal login + suspicious route probing → T1548 Priv Esc — investigate what they accessed after
🧠 The Overlap That Trips Analysts — Spray vs. Stuffing
T1110.003 (Spray) and T1110.004 (Stuffing) look identical at the IP/account level: same IP, low failure count per account, many accounts targeted. The single differentiator is the sprayed_password field in the event's extra column:
T1110.003 — Password Spray
extra: "sprayed_password=Summer2024!"
One password used against all accounts. Attacker picked a likely common password from a wordlist. Low-skill, high-volume.
T1110.004 — Credential Stuffing
extra: "reason=invalid_credentials"
No shared password. Each account gets its own credential pair from a breach dump. Higher-skill, targeted — attacker already has a list from a previous breach.
CISSP exam perspective: Both violate D5 (IAM authentication controls) but Stuffing indicates a pre-existing data breach (D7: Incident Response trigger), while Spray indicates a weak password policy (D5: access control failure).
